# TeamFlow deployment

TeamFlow is a Node.js application. Use Node.js 24 or the included Dockerfile. Provision PostgreSQL 16+, Redis 7+, an SMTP provider, and a private S3-compatible bucket. Place the application behind a TLS reverse proxy.

1. Set `DATABASE_URL`, `REDIS_URL`, `APP_URL`, SMTP settings, S3 settings, and `NEXT_PUBLIC_REALTIME_WS_URL` from `.env.example` in your secret manager. `APP_URL` must be the exact HTTPS origin users visit and `NEXT_PUBLIC_REALTIME_WS_URL` must be the browser-facing `wss://` URL ending in `/realtime`. Set the public WebSocket URL before building because Next.js embeds public environment values in the client bundle. Use a private bucket and least-privilege object credentials.
2. Run `npm ci`, `npx prisma generate`, and `npx prisma migrate deploy` as a release step. Do not use `prisma migrate dev` in production. When building the Docker image, pass `--build-arg NEXT_PUBLIC_REALTIME_WS_URL=wss://your-domain.example/realtime`.
3. Run `npm run build` and start application instances with `npm start`. Set `NODE_ENV=production` for the application, worker, realtime bridge, and WebSocket server. Run `npm run worker`, one `npm run realtime:bridge`, and one or more `npm run realtime:server` processes with the same database and Redis settings. The email worker claims jobs and retries failures with backoff. The bridge reads committed workspace events and publishes them to Redis; WebSocket servers subscribe and replay missed events from PostgreSQL.
4. Configure the reverse proxy to overwrite `X-Real-IP`, forward the original `Origin` and `Host`, enforce HTTPS, route `/realtime` with WebSocket upgrade headers to the realtime server, and prevent direct public access to Node.js ports. Keep `REALTIME_HOST=127.0.0.1` when proxying on the same host; use a private interface for separate hosts. Configure database backups and a tested restore procedure.
5. If Google login is needed, create a Google OAuth web client, register `${APP_URL}/api/auth/google/callback` as its redirect URI, and set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.
6. To grant platform administration to a verified user from a trusted deployment shell, run `npm run admin:grant -- admin@example.com`. Restrict shell access to trusted operators.
7. Monitor PostgreSQL connection pools, Redis availability, queued email age, realtime bridge lag, WebSocket connection counts, SMTP delivery, S3 errors, and HTTP 5xx rates. Run one bridge per deployment; WebSocket servers can scale horizontally through Redis pub/sub. Clients replay durable events after reconnect and deduplicate by event ID.
8. Run the full CI suite against the release candidate, test OAuth, SMTP, S3, and Redis with production-equivalent credentials, and verify a backup restore before accepting real data. Before applying the integrity-constraint migration to an existing database, check for invalid negative story points/positions, self-referential tasks or dependencies, oversized attachment records, and reversed sprint dates; the migration will reject such rows.

The local email and attachment adapters refuse to run in production. Do not run `npm run db:seed` in production. Production sessions are opaque, random, and stored in PostgreSQL. Email/password authentication and invitations use distributed Redis rate limits; if Redis is unavailable, production requests fail closed.
